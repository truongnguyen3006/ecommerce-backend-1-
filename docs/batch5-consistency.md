# Batch 5 consistency contracts

M03: `DomainException` carries stable action codes independently of HTTP status. Provider bodies and stack traces are absent from API errors. The frontend uses the code before its generic status fallback; a generic 409 does not imply stock shortage.

M04: invalid login, invalid refresh, disabled account, forbidden access, identity outage, configuration error and malformed token response are distinct. A transient refresh failure preserves the current session. A rejected grant or disabled account ends it. Mutations are never automatically replayed.

M05: each rendered admin variant queries stock with its own SKU; pagination and row ordering do not index an unrelated query array.

M06: category/color/size strip only outer ASCII spaces. Comparison keys use lowercase; display labels retain case, accents and interior whitespace. Search applies SQL trim/lower to legacy values without rewriting them. Case-equivalent labels collapse in navigation; semantically different interior spacing remains distinct. The database's existing collation can also affect comparisons; no accent-removal migration is performed. SKU identity is untouched.

M07: every product update includes the revision observed by that editor. A pessimistic parent lock compares the revision before modifying parent, children, SKU reservations or outbox. Success increments once; a stale request returns `PRODUCT_REVISION_CONFLICT` and commits nothing. Frontend editors retain their observed revision across background refetches, updating it only after their own successful save. A full refresh is required to review other edits. Product V5 is additive.

M08: Redis remains the cart authority. Every mutation changes a per-line revision, including a change back to the same quantity. An atomic Lua snapshot reads quantities and revisions together, assigning tokens to legacy lines conservatively. `POST /api/cart/purchased` authenticates the owner, reads that owner's accepted order using the JWT, verifies purchased SKU quantities, then executes one conditional Lua removal. It removes only matching quantity + revision lines. Missing legacy snapshot revisions are retained. A cleanup receipt and line tokens make retries safe, including after Redis AOF restart. Legacy asynchronous checkout uses the same conditional cleanup rather than deleting the whole cart. No cleanup runs for PENDING/failed/unowned orders. New/changed lines are preserved.

M09: all address mutations lock the owner's user row. Default changes clear and flush previous flags before choosing another. User V3 adds a generated nullable owner key with a unique index: at most one default per owner, including writes bypassing the service. Reviewed legacy repair keeps the lowest-ID default and changes only duplicate default flags; no address text or row is deleted. Deleting a default flushes its deletion then selects the lowest remaining address ID. Zero addresses implies zero defaults.

M10: public registration requires a stable `Idempotency-Key`. A separate committed SQL intent reserves normalized username/email before calling Keycloak. It stores a salted PBKDF2 request fingerprint, never a plaintext password or token. A locked intent serializes retries. Keycloak creation writes an admin-only `project1ProvisioningId` marker; recovery requires exact username, email, marker and any already recorded Keycloak ID before granting the configured USER role. Profile creation and intent completion share a SQL transaction. Provider/SQL/role failures leave a durable reconciliation intent; user retry with the same key/body rechecks provenance and finishes idempotently. No identity is deleted as compensation, no legitimate pre-existing identity is adopted. Pending intents are observable in `user_provisioning_intent` with state/attempts/safe error code. There is no credential-storing background worker.

The modern production realm template includes the managed marker with admin-only view/edit permissions. Existing realms are not overwritten by import; operators must append this attribute to their existing user-profile configuration after review. The service checks the policy before creating an identity and fails closed with `AUTH_CONFIGURATION_UNAVAILABLE` if absent. The legacy development Keycloak 18 configuration is not claimed compatible without enabling and verifying this profile capability. Production uses configured role `USER`; development retains existing `user`. Registration retries must retain their key; an abandoned browser attempt may require operator reconciliation instead of a new key. Direct Keycloak registration remains disabled in production.

M11: admin adjustments require a stable operation ID. An operation-ID repartition and persistent request store claim the first immutable payload globally before the existing SKU repartition. Kafka `exactly_once_v2` commits that claim and forward together. The stock task validates current quantity, writes stock and an immutable APPLIED/REJECTED result in one transaction. Duplicate delivery and replay of restored state cannot apply twice; a different payload cannot reuse the ID. HTTP acknowledgement is ACCEPTED, processing is PENDING, and only a terminal stored result proves application/rejection. Admin-only `GET /api/inventory/operations/{id}` returns safe operation status, never broker coordinates. A record not yet visible is PENDING, not guessed failed. Legacy compensation identity and deduplication remain unchanged.

The frontend stores unresolved stock operation IDs, quantity and acknowledgement state in owner/SKU-scoped session storage. Double submit is guarded. Uncertain retry retains its ID/body; reload reopens the saved operation. Inputs stay locked until a final result. Polling is bounded; the admin can check again without inventing a new operation. Status queries assume the existing single inventory-service instance; distributed interactive-query routing across multiple replicas is not implemented.

## Validation scope

Targeted tests cover status/code mapping, provider response classification, SKU pagination, facet collisions/legacy whitespace, concurrent and stale product edits, actual isolated Redis Lua concurrency/restart, owner/purchased-order validation, concurrent defaults plus database uniqueness and legacy repair, provisioning SQL/role failure injection and exact-origin checks, duplicate/conflicting/rejected stock operations, controller status, and replay after restoring committed Streams state. The Streams restoration fixture does not claim a live Kafka broker restart; that is a Batch 6 runtime scenario.

Backend test prerequisite: Java 24, Maven, and a Redis executable (`redis-server`, or `TEST_REDIS_EXECUTABLE`). Cart integration tests spawn their own loopback process and temporary directory, never connect to an existing Redis database. CI installs the executable. Full Batch 5 gate results are recorded in the final report.
