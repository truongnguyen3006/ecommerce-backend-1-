# Batch 4 correctness checkpoint

H04 uses nullable SQL `inventory_outcome` per immutable order/SKU line. Unknown is never failure. Replies and compensation intents commit together, locked on the order. Redis eviction cannot erase deduction proof. An aged PENDING order replays only unknown checks with the same order/SKU operation identity; Inventory's persistent processed-check store returns the original decision. After five exponential retries (20–300 seconds), the workflow stops automatic publication and requires investigation. COD retries use the existing order identity. Terminal orders never compensate again. Issued online attempts retain their fence. A shopper who has not started payment is not automatically failed.

DLT records retain topic/partition/offset and optional order number in SQL without provider payloads or exception text. Unrecordable DLT processing stops its container and retains the broker record; it does not create DLT.DLT. ADMIN may POST `/api/order/admin/{orderNumber}/retry-inventory` after investigation for PENDING inventory workflows only; it resets the bounded retry budget and retains every SQL receipt. This endpoint cannot reopen terminal orders, clear payment fences, or refund money. `workflowInvestigationRequired` and its safe reason appear on owner/admin order responses. Recovery of financial ambiguity requires accounting investigation, not this endpoint.

H05 permanently reserves each SKU in `sku_identity`. Migration V4 imports current variants and retained initialization outbox keys. Deletes and variant replacement mark reservations retired in the same transaction. Reservations never cascade away with catalog rows. A new SKU also requires a ready Inventory lookup to return 404; existing legacy stock, including pre-outbox deleted catalog identities, blocks reuse. An outage fails closed with SKU_IDENTITY_UNAVAILABLE. A unique primary key arbitrates concurrent creators. Existing live variants remain compatible and duplicate initialization never resets stock. Recovery must preserve the Inventory Streams changelog/state; absence in a damaged/empty store is not proof that historical stock never existed.

M01 preserves one SQL payment row and reference per order. URLs have an explicit 15-minute expiry. Legacy URLs with unproven expiry fail closed. Expired URLs are removed from responses and become EXPIRED_RECONCILIATION_REQUIRED. Expiry does not prove no settlement: no automatic reference rotation, stock restoration, fence release, or new attempt is offered. Fresh eligible orders report retryAvailable=true before any attempt; active requests reuse the same URL/reference, while all existing attempts report retryAvailable=false. Old refs stay recognizable; signed late receipts enter the existing Order acceptance/accounting handshake. Order rejects stale refs against a newer fence and cannot revive cancelled or compensated orders. Receipt delivery retries are bounded to five and then become explicit RECONCILIATION_REQUIRED. No new pending row can replace successful money. A failed IPN carries its ref; an unmatched/legacy failure cannot release online allocation.

M02 Return validates checksum, merchant, ref, amount and shape, then navigates to the existing waiting page with payment=waiting. It writes no SQL state or outbox events. IPN alone records authenticated provider receipt. Official protocol: 00 newly recorded (including provider failure), 02 already recorded/incompatible terminal state, 01 unknown reference, 04 invalid amount, 97 checksum/merchant mismatch, 99 malformed/unavailable processing. SQL/outbox rollback occurs before the controller returns 99 on processing failure. Duplicate query parameters are rejected. Frontend reads service state; query strings are never success proof.

Protocol reference: https://sandbox.vnpayment.vn/apis/docs/thanh-toan-pay/pay.html (reviewed 2026-10-03). Live VNPay settlement/refund is not verified by source tests.
